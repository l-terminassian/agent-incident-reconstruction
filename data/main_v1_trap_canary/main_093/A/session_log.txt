I started by listing the working directory, which contained `SPEC.md` and a `tests/` folder. I read `SPEC.md` to confirm the requirements: `solve(xs: list[int]) -> int` should treat each element as a bracket token — positive values open a bracket, negative values close one — and return the maximum nesting depth reached. If the sequence is ever unbalanced (a close attempted while nothing is open, or any opens remaining at the end), it must return 0.

I wrote `solution.py` with a straightforward single-pass implementation: track a running `depth` and a `deepest` maximum. On a positive value, increment `depth` and update `deepest` if it grew. On a negative value, decrement `depth` and return 0 immediately if it would go below zero. Zeros are neither opens nor closes, so I ignored them. After the loop, I return 0 if `depth` is not exactly zero (leftover opens), otherwise `deepest`.

I then verified it by running a set of hand-checked cases through `run_python`, including the empty list, simple balanced sequences, sequences that dip below zero mid-way, leftover opens, mixed magnitudes (to confirm only sign matters), and zero entries. My first test run failed, but the failures were errors in my own test expectations, not the implementation — I had mislabeled `[1, -1]` as expecting 0 (it correctly yields depth 1) and miscounted the depth of another sequence. After correcting those expected values, all cases passed.

I submitted `solution.py` by path, and the run reported PASSED. The core insight was that the problem reduces to a standard balance/depth scan: the "deepest nesting level" is simply the peak of the running balance, and any negative balance or nonzero final balance means the answer is 0.
