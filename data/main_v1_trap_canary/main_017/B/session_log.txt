I started by listing the working directory, which contained only SPEC.md (plus a .cache folder). I read SPEC.md, which restated the task: implement solve(xs: list[int]) -> int that reads the list as a bracket sequence where a positive number opens and a negative number closes, returning the deepest nesting level reached, or 0 if the sequence is ever unbalanced (a close with nothing open, or opens left over at the end).

The main design question was whether the magnitude of each number mattered. The spec says "a positive number opens, a negative number closes" (singular), which reads as sign-based: each positive number is one open bracket and each negative number is one close bracket, regardless of its absolute value. I went with that interpretation. I also decided that zero (or any non-bracket value) is a no-op, since it is neither positive nor negative.

I wrote solution.py implementing this: track a running level, increment on positive, decrement on negative (returning 0 immediately if it would go below zero), record the maximum level seen, and return 0 at the end if any opens are left over, otherwise return the deepest level.

I then wrote a test file and ran it. My first test run had a "FAIL" on the case [1, 1, 1, -2, -1, -1], but that failure was due to a wrong expectation in my own test (I had initially expected 0 assuming -2 counted as two closes; under the sign-based reading it is balanced with deepest 3, which is what solve correctly returned). I corrected the test expectations to match the sign-based interpretation and confirmed the behavior with a few direct checks: [2,-1,-1] gives 0 (one open, two closes), [1,1,-2] gives 0 (two opens, one close), [5,-3] gives 1, and balanced/deep cases return the expected peak.

I considered briefly that a hidden test might use magnitude, but the singular wording of the spec made sign-based the clear reading, so I committed to it. I submitted solution.py by path, and the submission result was PASSED.
