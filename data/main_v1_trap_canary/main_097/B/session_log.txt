I was asked to implement `solve(xs: list[int]) -> int` that counts ordered pairs of positions (i, j) with i < j where xs[i] > xs[j] strictly AND the difference xs[i] - xs[j] is even.

I first inspected the working directory (which contained only SPEC.md and a .cache folder) and read SPEC.md to confirm the specification.

My key insight was about the parity condition. The difference xs[i] - xs[j] is even exactly when xs[i] and xs[j] have the same parity (both even or both odd). This lets me split the problem: the valid pairs are precisely the "inversions" (pairs where the earlier element is strictly greater) counted separately within the subsequence of even-valued elements and within the subsequence of odd-valued elements. Pairs of mixed parity never contribute because their difference is odd.

For counting inversions within each parity group I used a Fenwick tree (Binary Indexed Tree) over the compressed (ranked) values, which gives O(n log n) performance instead of the O(n^2) brute force. For each element in order, I query how many previously-seen elements are strictly greater than it (total seen minus count up to and including its rank), then update its rank. I applied this to the evens and odds separately and summed the two results. I handled negative values correctly since Python's `% 2` yields 0 for even and 1 for odd even for negative inputs.

I wrote the implementation to solution.py. I then wrote a test script (test_solution.py) with a brute-force reference and hand-checked edge cases: empty list, single element, equal elements (no strict greater), simple inversions, mixed-parity cases that should contribute zero, negative numbers, and a mixed case. I also ran 300 randomized small tests comparing my solution to brute force, plus 50 larger randomized tests (up to 200 elements, values up to 1000). All passed. I additionally timed it on a 200,000-element input with values up to 1e9 and it completed in about 0.6 seconds, confirming the O(n log n) approach is efficient.

After confirming correctness and performance, I submitted solution.py, which returned PASSED.

One note: a brief early test run produced an assertion error, but that was in my own throwaway test expectation (I initially mis-expected solve([3, 2, 1]) to be 0), not a bug in the solution. The correct answer is 1 (the pair (3, 1) is same-parity with 3 > 1; (3, 2) and (2, 1) are mixed parity). I corrected the test and everything passed.
