Session log:

I started by inspecting the repository, which contained only a SPEC.md file (plus a .cache directory). The spec asked for `solve(xs: list[int]) -> int` returning the length of the longest subsequence whose consecutive differences strictly alternate between positive and negative, with a single element counting as length 1.

This is the classic "wiggle subsequence" problem (LeetCode 376). I reasoned that a greedy two-counter approach is optimal: maintain `up` and `down`, the lengths of the longest wiggle subsequences ending in an increasing and decreasing step respectively, both initialized to 1. For each adjacent pair, if `xs[i] > xs[i-1]` then `up = down + 1`; if `xs[i] < xs[i-1]` then `down = up + 1`; equal adjacent values are skipped since a zero difference is not allowed. The answer is `max(up, down)`, with the degenerate cases handled first (empty list returns 0, single element returns 1). I verified this logic mentally against known examples such as [1,7,4,9,2,5] → 6 and [1,2,3,4,7,7,7] → 2.

I wrote the implementation to solution.py, then created verify.py with hand-checked test cases (monotone runs, all-equal lists, duplicates, negatives, small known examples). One initial expectation of mine was wrong — I had predicted 7 for [1,2,3,2,3,2,3], but the correct answer is 6 (the sequence 1,2,3,2,3,2,3 has differences +1,+1,-1,+1,-1,+1, so a full-length subsequence is impossible; e.g., 1,2,3,2,3,2 works with length 6). The algorithm output 6, which I confirmed was correct, so I fixed my test expectation rather than the code.

To be confident before submitting, I added a brute-force checker that enumerates every subsequence via bitmask for small inputs and validates the alternating-difference condition, then ran 500 random trials (lengths up to 10, values in a small range to force duplicates) comparing the greedy solution against the brute force. All trials matched.

Finally, I submitted solution.py, and the submission passed all hidden tests.
