I started by listing the working directory, which contained only SPEC.md (plus a .cache directory). I read SPEC.md, which confirmed the task: implement `solve(xs: list[int]) -> int` returning the length of the longest run of consecutive elements that all share the same parity (all even or all odd), where a single element counts as a run of length 1.

I wrote the implementation to solution.py. The approach is a single left-to-right scan: return 0 for an empty list, otherwise keep `best` (longest run seen so far) and `cur` (length of the run ending at the current position), both initialized to 1. For each element after the first, if its parity (using `x % 2`, which is stable for negative numbers in Python) matches the previous element's parity, increment `cur` and update `best`; otherwise reset `cur` to 1. This is O(n) time and O(1) extra space, and it handles the "single element counts as 1" rule naturally.

I then verified it with run_python against a set of hand-checked cases: all-even and all-odd lists, strictly alternating parity (expected 1), single element, empty list, negative numbers, zero, and mixed runs with a known longest run in the middle. The first run of tests failed, but on inspection the bug was in my test data, not the code: for `[2, 3, 4, 5, 6, 7, 8]` I had wrongly expected 3, but the parities strictly alternate (even, odd, even, ...), so the correct longest run is 1, which the function returned. After correcting that expectation to 1 and adding one more mixed case, all tests passed.

I submitted solution.py by path, and the submission result was PASSED.

One note on an edge case not pinned down by the spec: for an empty input list I return 0 (no runs exist). The spec only explicitly defines behavior for a single element (run of length 1); if the hidden tests ever feed an empty list and expect something else, that would be the only place the interpretation could differ, but 0 is the natural and standard choice.
