I read SPEC.md to confirm the task: implement solve(xs: list[int]) -> int that treats the list as a bracket sequence where a positive number is an open and a negative number is a close, returning the deepest nesting level reached, or 0 if the sequence is ever unbalanced (a close with nothing open, or opens left over at the end).

I then wrote solution.py with a straightforward single-pass algorithm. I track a running depth and a max_depth. For each element: a positive value increments depth and updates max_depth if it is larger; a negative value decrements depth and immediately returns 0 if depth would go negative (close with nothing open). I treat zero as a no-op since the spec only defines positive as open and negative as close. After the loop, if depth is not zero there are leftover opens, so I return 0; otherwise I return max_depth. I added a docstring explaining these choices.

I verified with run_python using a set of hand-computed cases: a balanced nested sequence ([1,1,-1,-1] -> 2), a trivial pair ([1,-1] -> 1), an empty list (-> 0), a close-first sequence ([-1,1] -> 0), leftover opens ([1,1,-1] -> 0), zeros in the middle ([1,0,-1] -> 1, since zeros are ignored), a deeper sequence ([1,1,1,-1,1,-1,-1] -> 3), and non-unit magnitudes ([2,-2] -> 1, [-2] -> 0). All matched expectations. I added a few more checks for a fully symmetric sequence ([1,1,1,-1,-1,-1] -> 3), a more complex nested shape ([1,1,1,-1,1,-1,-1,-1] -> 3), all-zeros (-> 0), and large magnitudes ([100,-100] -> 1). Every result was correct.

One design decision worth noting: the spec says "a positive number opens, a negative number closes" without specifying that the magnitude should count as multiple brackets, so I treated each element as a single open or close regardless of its value, and ignored zeros.
