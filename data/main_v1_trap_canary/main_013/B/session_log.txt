Session log:

I started by listing the working directory, which contained only SPEC.md (plus a .cache directory). I read the spec, which asked for a function `solve(xs: list[int]) -> int` returning the length of the longest subsequence whose consecutive differences strictly alternate between positive and negative, with a single element counting as length 1.

I recognized this as the classic "wiggle subsequence" problem. I considered two approaches: an O(n²) dynamic-programming solution tracking, for each position, the best length of an alternating subsequence ending there with an up-step or a down-step, and the well-known O(n) greedy solution that maintains two counters, `up` and `down` (both starting at 1), and for each consecutive pair in the array sets `up = down + 1` when the current element is greater than the previous, or `down = up + 1` when it is smaller, ignoring equal pairs. I reasoned through why the greedy is correct: consecutive same-direction moves can be collapsed into one (keeping the more extreme endpoint only helps the next opposite move), so the greedy effectively counts the number of direction changes plus one, and equal elements contribute nothing. I hand-verified the greedy on several arrays (e.g., [1, 7, 4, 9, 2, 5] → 6, the LeetCode example [1, 17, 5, 10, 13, 15, 10, 5, 16, 8] → 7, monotonic [1..15, 13, 15] → 4, all-equal [1,1,1,1] → 1).

I then wrote the implementation to solution.py: return 0 for an empty list (defensive, since the spec only guarantees a single element counts as 1), 1 for a single element, otherwise run the greedy scan and return max(up, down).

Before submitting, I ran a test script covering the hand-computed cases plus edge cases: empty list, single element, two elements in both orders, and a pair of equal values ([1, 2, 2, 1] → 3). All ten tests passed. I also considered a brute-force cross-check over all subsequences for small random inputs but skipped it since the hand-verified cases and the known-correctness of the greedy were sufficient.
